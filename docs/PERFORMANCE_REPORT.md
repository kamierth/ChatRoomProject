## 2. 测试目标

本轮测试用于确认以下能力：

1. 核心聊天功能在真实 TCP 连接下可以正常工作。
2. 多个客户端并发发送消息时，服务端能够完成广播投递且不会出现测试可见错误。
3. 单个客户端停止读取数据时，不会导致其发送队列无限增长，也不会拖垮正常客户端。
4. 服务端收到 `SIGINT` 或 `SIGTERM` 后能够正常退出并释放连接。
5. 建立一组可重复执行的性能基线，为后续 Reactor、线程池和协议优化提供对照数据。

## 3. 被测系统

### 3.1 服务端实现

- C++17 单线程事件循环。
- 非阻塞 TCP Socket。
- Linux `epoll`，当前使用水平触发模式。
- 换行符分隔的纯文本协议。
- 每连接独立的接收与发送缓冲区。
- 发送队列高低水位背压：
  - 高水位：256 KiB；
  - 低水位：128 KiB；
  - 硬上限：1 MiB。
- 发送队列达到高水位时暂停该连接的 `EPOLLIN`，降至低水位后恢复。
- 新数据会导致队列超过硬上限时，断开对应慢客户端。
- 使用 `signalfd` 将 `SIGINT`、`SIGTERM` 纳入事件循环。

### 6.2 50 客户端并发压力测试

执行参数：

```bash
python3 scripts/load_test.py \
    --host 127.0.0.1 \
    --port 8080 \
    --clients 50 \
    --messages 20 \
    --payload-size 32
```

| 指标 | 结果 |
| --- | ---: |
| 计划连接数 | 50 |
| 成功连接数 | 50 |
| 连接成功率 | 100% |
| 计划发送消息数 | 1,000 |
| 成功发送消息数 | 1,000 |
| 消息发送成功率 | 100% |
| 聚合客户端提交速率 | 约 2,841 msg/s |
| 客户端接收总行数 | 52,500 |
| 脚本错误数 | 0 |

1,000 条聊天消息均广播给 50 个在线客户端，对应 50,000 条聊天投递。其余 2,500 行来自用户加入和离开通知，因此接收总行数 52,500 与当前协议行为一致。

需要注意：`2,841 msg/s` 是压力脚本中所有客户端完成 `sendall()` 的聚合速率。TCP `sendall()` 成功只表示数据已交给本机内核发送缓冲区，不代表所有接收方已经处理完消息。因此该数值不能替代服务端端到端吞吐量或延迟分位数。

结果：通过本轮设定的 50 客户端基础并发目标。

### 6.3 慢客户端与背压测试

执行参数：

```bash
python3 scripts/slow_client_test.py \
    --host 127.0.0.1 \
    --port 8080
```

| 指标 | 结果 |
| --- | ---: |
| 测试连接 | 1 个慢客户端，1 个正常客户端 |
| 广播消息数 | 256 |
| 单条测试负载 | 32,768 bytes |
| 生成的消息负载 | 8,388,608 bytes |
| 测试用时 | 1.24 s |
| 慢客户端结果 | 被服务端移除 |
| 正常客户端结果 | 保持连接并能执行 `/list` |

测试期间记录到的关键状态：

```text
client receive paused by backpressure fd=6 queued_bytes=271623
disconnecting slow client fd=6 queued_bytes=1026161 incoming_bytes=32806 limit=1048576
```

高水位为 262,144 bytes。日志中的暂停值略高于高水位，是因为消息按完整块加入队列，水位判断发生在一次追加和发送尝试之后。断开前队列为 1,026,161 bytes，新消息为 32,806 bytes；两者之和将超过 1,048,576 bytes 硬上限，因此新消息未进入队列，慢客户端被移除。

结果：通过。应用层单连接发送队列不会超过 1 MiB，正常客户端在慢客户端被清理后仍然可用。

结果：通过。

## 7. 结果分析

### 7.1 已确认的能力

1. 单线程 `epoll` 架构能够稳定完成本轮 50 客户端、1,000 条输入消息和约 50,000 次聊天广播投递。
2. 测试中未发生连接失败、消息发送失败或压力脚本异常。
3. 每连接 1 MiB 的硬上限限制了应用层发送队列的最坏内存占用。
4. 高低水位迟滞机制避免在单一临界值附近频繁启停 `EPOLLIN`。
5. 慢客户端被隔离后，正常客户端仍可继续通信和查询在线列表。

### 7.2 当前架构的主要性能特征

- 群聊广播复杂度约为 `O(在线人数)`，总投递量随在线人数平方级放大。
- 服务端为单线程，协议处理、日志、连接管理和 Socket 收发共享同一个事件循环线程。
- `std::string::erase(0, size)` 在部分发送时可能移动剩余数据，较大队列下存在额外复制成本。
- 同步日志会增加事件循环中的 I/O 和锁开销，压力测试时应降低日志级别或使用异步日志。
- 当前背压是按连接控制的，尚未设置服务端全局待发送内存上限、最大连接数或按 IP 限流。

## 9. 后续性能测试建议

建议下一轮按照以下顺序建立更完整的性能基线：

1. 使用 `cmake -DCMAKE_BUILD_TYPE=Release` 重新构建，分别测试 50、100、500 和 1,000 个连接。
2. 在协议中加入消息序号和发送时间，统计端到端 P50、P95、P99 延迟。
3. 使用 `/usr/bin/time -v`、`pidstat` 或 `perf stat` 同时记录 CPU、RSS、上下文切换和系统调用。
4. 进行至少 30 分钟的稳定性测试，观察连接数、内存和文件描述符是否持续增长。
5. 使用 `tc netem` 模拟延迟、限速和丢包，继续验证背压与慢客户端清理。
6. 优化发送缓冲区的数据结构后，使用相同参数复测并比较，而不是只比较单次最高值。

## 10. 最终结论

ChatRoomProject 已通过当前阶段的自动化测试、真实 Socket 集成测试、50 客户端并发压力测试、慢客户端保护测试和人工功能验收。测试结果证明现有实现具备正确的基础并发处理能力，并能通过高低水位背压和单连接硬上限控制慢客户端风险。

本轮结果适合作为项目当前版本的开发性能基线，也足以说明服务端具备非阻塞 I/O、事件驱动、缓冲区管理、背压和异常连接隔离能力。但由于尚未采集资源占用、延迟分位数、大规模连接和长时间运行数据，不应将本报告解释为生产环境容量证明。
